**Backend release changes**

These changes are additive to the existing schema. Deploy the backend and matching clients together: writes now require acceptance of terms version `2026-10-20`; old clients cannot acknowledge that version. Do not deploy a terms gate without the matching welcome/account UI.

- Account deletion marks the account immediately unavailable, then runs bounded resumable cleanup. It revokes auth sessions/refresh tokens/accounts/codes/verifiers, removes the person's ratings, uploads, photos and wishlist, and clears their authored notes and authorship. Shared factual visit/place/date/dish records and other members' contributions remain. Notes now track their latest editor; legacy notes without attribution use the original visit creator as the fallback. Shared-board ownership passes to a remaining member/admin; solo boards are deleted. Local file cleanup completes when the configured local photo service is available. Existing downloaded copies and independent backups are outside that cleanup.
- Block and leave immediately leaves the originating board and separates remaining shared memberships in bounded jobs. Future join/approval operations reject co-membership in either direction. Unblocking does not restore memberships. An account-deletion job and a pending block job are retried every 30 minutes if interrupted.
- Safety reports are limited to content/current people on boards the reporter can access. Ten reports per hour per person are accepted; support email remains available beyond that limit. Reports contain the submitted reason, content identifiers, timestamps and resolution. Content summaries are computed live for authorized moderation; no duplicate notes/photos snapshot is kept. Photo reads are authorized for moderators only while an associated report is open. Reports are deleted with their board; a deleting person's reports are removed and targeted account references are deidentified.
- Moderator access requires a configured email, a verified email timestamp, and an authenticated Google provider account. `MODERATOR_EMAILS` is a comma-separated allowlist; the default is `nishit.nagar1@gmail.com`. Native Google verification now records the verified email timestamp from its verified signed token. Older browser-only accounts without that verified marker must sign in through the native client, or an operator must verify/reconcile their existing auth record before granting access. The reported content must actually be reviewed; building a queue does not provide staffed moderation.
- `photos.configuration` exposes the public support email and `localStorageReady`. Choosing local storage requires both `LOCAL_PHOTO_SECRET` and `LOCAL_PHOTO_ENABLED=true`. Existing local images remain readable if the opt-in flag is off. This flag is an operator declaration that the service is reachable; monitor that service separately.
- Upload completion is recoverable for the photo's lifetime by `photos.uploadId` (cloud) or `localKey` (local). Completed reservation records expire after a day; their removal does not break completed-operation reconciliation. An incomplete expired ticket returns `UPLOAD_EXPIRED`/HTTP 410. Only confirmed expiry should create a fresh reservation; uncertain network errors should retry the original operation. Existing pre-upgrade cloud photos do not retroactively acquire missing upload IDs.
- Visit edits accept `expectedRevision` and reject stale saves with an actionable message. Canonical place-detail changes also increment the revision. The optional argument preserves compatibility for older callers; release clients should always send it.
- Board counts are maintained transactionally for new boards and populated in bounded jobs for existing boards. `summaries.visitCount` is `null` while preparing; clients should render a pending value. Call `boards.ensureCounts` on visible boards. After an authorized deployment, an operator can run `boards:backfillCounts` with `{"cursor":null}` against the intended deployment. No data is deleted by this backfill.
- Wishlist update validates http/https links and preserves canonical place information. `visits.create` can receive `wishlistId` and `keepWishlist`; removal occurs only transactionally after successful validation when `keepWishlist` is explicitly false.

The privacy policy, store declarations, support staffing/response time, final production environment and backup retention must match real operations. This code provides in-app safety/reporting, moderation actions and blocking for private groups; it is not an automated image-classification service.
